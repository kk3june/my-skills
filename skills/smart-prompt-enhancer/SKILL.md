# Smart Prompt Enhancer

사용자의 요청을 분석하여 모호성을 식별하고, 프로젝트 컨텍스트를 활용해 최적의 구현 방식을 제안합니다.

## 목적

1. **모호한 요청 명확화** - 불완전한 요구사항에서 구체적 선택지 도출
2. **컨텍스트 기반 제안** - 프로젝트 기술 스택에 맞는 구현 방식 추천
3. **Best Practice 적용** - 공식 문서 기반 패턴으로 고품질 코드 보장

---

## 활성화 조건

다음 상황에서 자동 활성화됩니다:

### 1. 구현 방식이 여러 개인 경우

```
사용자: "로그인 기능 만들어줘"

분석:
- 인증 방식: JWT / Session / OAuth 중 선택 필요
- 폼 구현: 제어/비제어 컴포넌트 선택 필요
- 상태 저장: Cookie / LocalStorage / 메모리 선택 필요
```

### 2. 기술 선택이 필요한 경우

```
사용자: "전역 상태 관리 추가해줘"

분석:
- 프로젝트에 이미 Jotai 있음 → Jotai 확장 권장
- 새 라이브러리 도입 시 → 장단점 비교 제시
```

### 3. 아키텍처 결정이 필요한 경우

```
사용자: "API 호출 로직 분리해줘"

분석:
- Custom Hook 패턴
- Service Layer 패턴
- Repository 패턴
→ 프로젝트 규모와 기존 구조에 맞는 방식 제안
```

## 분석 프로세스

### Step 1: 컨텍스트 확인

```
.claude/project-context.md 존재 여부 확인
├── 있음 → 기술 스택 정보 활용
└── 없음 → package.json 직접 분석 또는 컨텍스트 생성 안내
```

### Step 2: 요청 분석

사용자 요청에서 다음을 식별:

| 분석 항목 | 예시 |
|----------|------|
| **대상** | 어떤 기능/컴포넌트 |
| **동작** | 생성/수정/삭제/리팩토링 |
| **범위** | 단일 파일/여러 파일/전체 구조 |
| **제약사항** | 명시된 기술/패턴 제한 |
| **모호성** | 불명확한 부분 |

### Step 3: 선택지 도출

모호한 부분에 대해 구현 선택지 생성:

```typescript
interface ImplementationChoice {
  option: string           // 선택지 이름
  description: string      // 간단한 설명
  pros: string[]          // 장점
  cons: string[]          // 단점
  recommendation: boolean  // 프로젝트에 권장 여부
  reason?: string         // 권장/비권장 이유
}
```

## 응답 형식

### 선택지가 필요한 경우

```markdown
## 요청 분석

**대상**: {기능/컴포넌트}
**동작**: {생성/수정/etc}

---

## 구현 방식 선택

다음 중 선택해주세요:

### 1️⃣ {Option A} ⭐ 권장
> {한 줄 설명}

**장점**
- {장점 1}
- {장점 2}

**권장 이유**: {프로젝트 컨텍스트 기반 이유}

---

### 2️⃣ {Option B}
> {한 줄 설명}

**장점**
- {장점 1}

**단점**
- {단점 1}

---

### 3️⃣ {Option C}
> {한 줄 설명}

**장점**
- {장점 1}

**단점**
- {단점 1}

---

💡 **추가 확인 필요**
- {추가로 확인이 필요한 사항}

원하시는 방식을 선택하시거나, 추가 요구사항을 말씀해주세요.
```

### 명확한 요청인 경우

선택지 없이 바로 구현을 진행합니다:

```markdown
## 요청 분석

**대상**: {기능/컴포넌트}
**동작**: {생성/수정/etc}
**구현 방식**: {자동 선택된 방식}

---

구현을 진행합니다.
```

## 분석 예시

### 예시 1: 인증 기능

```
사용자: "로그인 기능 만들어줘"

프로젝트 컨텍스트:
- Next.js 15 (App Router)
- Supabase 사용 중
- React Hook Form + Zod

응답:
## 요청 분석

**대상**: 로그인 기능
**동작**: 신규 생성

---

## 구현 방식 선택

### 1️⃣ Supabase Auth ⭐ 권장
> 프로젝트에 이미 Supabase가 있으므로 통합된 인증 사용

**장점**
- 이미 설정된 인프라 활용
- 소셜 로그인 확장 용이
- RLS와 자연스러운 연동

**권장 이유**: 프로젝트에 Supabase가 이미 구성되어 있습니다.

---

### 2️⃣ NextAuth.js
> 독립적인 인증 레이어 구성

**장점**
- 다양한 Provider 지원
- 세션 관리 유연성

**단점**
- 추가 설정 필요
- Supabase와 별도 관리

---

### 3️⃣ 커스텀 JWT
> 직접 구현한 토큰 기반 인증

**장점**
- 완전한 제어권

**단점**
- 보안 구현 복잡
- 유지보수 부담

---

💡 **추가 확인 필요**
- 소셜 로그인 필요 여부 (Google, GitHub 등)
- 이메일 인증 필요 여부
```

구현 내용:

## 컨텍스트 연동

### project-context.md 활용

```
감지된 기술 스택 → 구현 방식 자동 필터링

예:
- Zustand 감지 → 전역 상태는 Zustand로
- TanStack Query 감지 → 서버 상태는 TanStack Query로
- React Hook Form 감지 → 폼은 RHF + Zod로
```

### project-patterns.md 활용

```
프로젝트 패턴 → 코드 스타일 일관성 유지

예:
- 훅 네이밍: use{Resource}Query
- 컴포넌트 구조: 기존 패턴 따름
- 에러 처리: 프로젝트 표준 방식
```

## 스킵 조건

다음 경우 선택지 제시 없이 바로 진행:

1. **명시적 지시** - "Zustand로 만들어줘"
2. **단순 작업** - "오타 수정해줘", "버그 고쳐줘"
3. **유일한 방법** - 프로젝트에 하나의 선택지만 있을 때
4. **이전 결정 존재** - 같은 세션에서 이미 선택한 방식
